# Tenancy and authorisation
The browser never sets authoritative tenant context. Session lookup joins an active user; its tenant enters `scoped()` which BEGINs, sets a transaction-local app.tenant_id, executes parameterised queries and COMMITs/ROLLBACKs before releasing the connection. RLS is ENABLED and FORCED on tenant content tables. `vestry_app` is NOSUPERUSER/NOBYPASSRLS. Tenant foreign keys prevent cross-church relationships even with guessed UUIDs.

Routes apply permission middleware. Default roles are in server/security.ts. Per-user grants can extend defaults and explicit denials override them; Administration exposes the permission matrix. Super administrators and archdiocese administrators can select an authorised parish using X-Parish-Id. The API validates the session role and archdiocese ownership on every request before setting transaction-local parish context; parish users cannot override their assigned parish. The same forced RLS policies apply to central and parish access. Central changes require X-Change-Reason and retain the central actor identity. See ARCHDIOCESE_GUIDE.md.

Sessions contain only random server-side keys, hashed in the database. Cookie is HttpOnly, SameSite=Strict and Secure in production. Writes require configured Origin and session CSRF header. File GETs require download permission and create an audit event. Staff access changes revoke all their sessions. MFA uses standard TOTP, encrypted with an environment key. Production admin/priest/platform/archdiocese accounts can access only security setup until enrolled. Enabling MFA revokes other sessions. Configure and approve an MFA recovery procedure before exposing real data.

Staff access changes also invalidate outstanding invitation/reset tokens. A reset never activates an inactive account; invitation acceptance is the only token path that activates a pending staff account. Register responses return only a minimal event identity when member permission is denied, and certificate listing responses omit the internal issuance snapshot. Security events include login/logout, recovery, MFA setup/enrollment and session revocation.

## Forane extension

The forane_admin oversight role requires an archdiocese/forane identity and no parish identity. Every selected parish is checked against both identities, including file requests. Forane tables use forced RLS with transaction-local office settings derived from the authenticated account; existing parish records remain parish-scoped. Parish participation policies permit only the user's own non-withdrawn reports. API responses omit office minutes, observations, follow-up and other parishes' responses. See [FORANE_GUIDE.md](FORANE_GUIDE.md).
